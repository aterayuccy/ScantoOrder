# Scan to Order 掃描點餐

一套以 QR Code 為入口的點餐系統，包含店家菜單管理、顧客品項調整、購物車、訂單與付款流程。

這是我在剛畢業、準備進入職場時完成的全端作品。最初只是想做一個可以掃碼點餐的網站，但在開發過程中，我發現真正的點餐系統不只是新增、修改、刪除品項，還需要考慮不同店家的使用情境、顧客操作流程、價格安全、付款狀態與手機版體驗。

因此，我把它逐步整理成一個可以完整展示前後端整合能力的作品。

## 專案動機

許多餐飲系統會直接使用「尺寸、甜度、冰量」等欄位，但這種設計容易把系統限制在飲料店。

我希望這個網站可以同時套用在飲料店、牛排館、早餐店或一般餐廳，因此將品項調整設計成由店家自行設定的通用步驟，例如：

- 內容調整：大杯、小杯、熟度或份量
- 口味調整：甜度、醬料或辣度
- 加購：飲料、配餐或甜點
- 備註或特殊需求

每個選項都能設定加價、折抵或維持原價，讓同一套結構能適用在不同類型的店家。

## 主要功能

### 店家端

- 使用唯一的使用者名稱註冊及登入
- 建立、修改與刪除品項
- 設定品項分類、價格、說明及圖片
- 自行設定品項調整步驟數量
- 設定單選或複選內容
- 設定選項的加價或折抵金額
- 產生、下載及刪除桌號 QR Code
- 查看顧客選擇的品項內容與備註
- 查看店家訂單及付款狀態
- 處理店內付款與手機條碼載具狀態

### 顧客端

- 掃描桌號 QR Code 後直接進入菜單
- 依分類瀏覽及搜尋品項
- 選擇店家設定的品項調整內容
- 查看調整後單價與購物車小計
- 填寫備註或特殊需求
- 選擇店內付款或 LINE Pay
- 選擇是否開立發票及輸入手機條碼載具
- 查看送出後的訂單與付款資訊

### 帳號與安全

- 使用者名稱具有唯一性
- 密碼長度限制為 8～64 個字元
- 密碼必須同時包含英文字母與數字
- 密碼以雜湊方式儲存，不保存明文
- 使用 JWT 驗證店家與顧客身分
- 後端重新計算品項價格，不直接信任前端傳入的金額
- 限制圖片格式、大小，並檢查實際檔案內容
- 店家只能存取自己的品項、QR Code 與訂單資料

## 使用流程

1. 店家註冊並登入帳號。
2. 店家建立菜單與品項調整選項。
3. 店家依桌號產生 QR Code。
4. 顧客掃描 QR Code，系統自動建立該桌的臨時顧客身分。
5. 顧客選擇品項、完成內容調整並加入購物車。
6. 顧客選擇付款與發票方式後送出訂單。
7. 店家在訂單頁確認品項、付款及載具處理狀態。

## 本機執行

### 1. 準備環境

請先安裝：

- Node.js 20 或以上版本
- MongoDB

### 2. 安裝套件

```bash
npm install
```

### 3. 設定後端環境變數

將 `server/.env.example` 複製為 `server/.env`，至少設定：

```env
PASSPORT_SECRET=請替換為足夠長的隨機字串
MONGODB_URI=mongodb://localhost:27017/mernDB
PORT=8080
CLIENT_BASE_URL=http://localhost:8080
```

如果沒有填入 LINE Pay 憑證，系統會使用內建的付款展示流程。

### 4. 建置並啟動

```bash
npm run build
npm start
```

開啟：

```text
http://localhost:8080
```

## 設計上的考量

### 為什麼不用電子信箱登入？

這個版本以作品展示及店內快速使用為目標，因此改用較短的唯一使用者名稱。這樣可以降低店家註冊時的輸入負擔，也不需要額外維護驗證信服務。

代價是目前沒有忘記密碼與信箱找回功能。如果未來要正式營運，我會加入信箱或手機驗證，補上完整的帳號復原流程。

### 為什麼價格一定要由後端計算？

前端傳來的價格可以被修改，因此後端只接收顧客選擇的選項 ID，再依資料庫中的原價、加價與折抵重新計算。這是我在製作購物車時特別重視的安全設計。

### 為什麼先做 LINE Pay 展示流程？

真實 LINE Pay 需要店家申請商家帳號、Channel ID 與 Channel Secret。為了讓作品在沒有正式商家憑證時仍能完整展示付款前後的畫面與狀態，目前預設使用展示流程；後端已保留 Sandbox 串接設定。

## 目前限制

- LINE Pay 預設為展示模式，真實付款需要合法商家憑證。
- 圖片若部署在 Railway，需要掛載 Volume 或改用物件儲存服務。
- 目前沒有忘記密碼與帳號復原功能。
- 發票功能目前著重於載具資料與店家處理狀態，尚未串接正式電子發票加值中心。
- 這是個人作品，尚未進行大量使用者與高流量壓力測試。

## 我從這個專案學到的事

剛開始做這個作品時，我比較容易直接從畫面與功能出發；做到後面才慢慢理解，完整的系統需要同時考慮資料結構、權限、例外狀況與使用者操作順序。

這個專案讓我實際練習到：

- 將模糊需求拆成可以實作的資料結構與 API
- 在前端操作方便與後端資料安全之間取得平衡
- 處理桌面版與手機版不同的版面需求
- 為重要流程撰寫自動驗證腳本
- 誠實區分「展示功能」與「正式商用串接」
- 從單純完成畫面，進一步思考整體使用流程

我知道這個專案還有許多可以改進的地方，但它完整記錄了我從需求討論、資料建模、前後端實作、除錯到部署準備的學習過程。
